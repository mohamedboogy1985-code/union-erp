# تقييم مقترح «Dynamic Agent Swarm / Computer Agent»

> **السؤال:** هل المقترح (منسّق سرب ديناميكي + مسجّل وكلاء + حالة مهمة مشتركة + Critic/Verification +
> مُعيد تخطيط + وكلاء رؤية/متصفح/ويندوز/بحث) مفيد لهذا المشروع؟
>
> **الجواب المختصر:** ~25% منه مفيد فعلاً، و~50% **موجود بالفعل** في المستودع، و~25% **خارج نطاق المشروع**
> ولا أنصح بتنفيذه. والأهم: الثلاثة الأجزاء المفيدة ليست معمارية جديدة، بل **أربعة عقود تشغيلية**
> تُصلح أكبر نقطة ضعف في سطح `AetherSwarm` القائم.

---

## 1) لماذا 50% منه موجود بالفعل

المشروع يملك سطحاً كاملاً اسمه **AetherSwarm** يغطّي معظم طبقات المقترح:

| ما يقترحه المقترح | الموجود في المستودع | الدليل |
|---|---|---|
| Swarm Orchestrator | `/api/swarm/orchestrate` + `generateCognitiveSwarmPlan` | `server/routes/aetherswarm.routes.ts` (920 سطراً) |
| Agent Registry | مصفوفة 6 وكلاء مع DNA (capabilities/limitations/tools/confidenceRequired) | نفس الملف، الأسطر 43–120 |
| Task Graph / DAG | `taskGraph` (قالب ثابت لكل نوع طلب) | نفس الملف، `isRtxPrompt ? ...` |
| Agent Dispatcher | `/api/swarm/execute-step` | السطر 571 |
| Evidence / Critic / Conflicts | `agent-critic` + `blackboardSeed` + `/api/swarm/resolve-conflict` | الأسطر 89–105، 253، 636 |
| Vision / Browser / Windows / Data Agents | وكلاء بأسماء وقدرات نصية | الأسطر 58–119 |
| Permission / Safety Layer | `PermissionModal` + `complianceGate` + RBAC حقيقي على المسارات | `src/aetherswarm/components/PermissionModal.tsx`، `server.ts` (`requirePermission`) |
| Audit / Memory / Blackboard UI | `AuditLogView`، `MemoryMatrixView`، `SwarmBlackboard` | `src/aetherswarm/components/` |
| Execution Safety Layer (حقيقي) | سجل تدقيق متسلسل بالتجزئة + وضع مصادقة صارم | `server/services/audit-chain.service.ts`، `server/security/runtime-config.ts` |

مصدر إضافي: `docs/AI_AGENT_AUDIT.md:72` يقيّم هذا السطح نفسه بأنه **خطة ثابتة + مخرجات محاكاة**.

## 2) لماذا 25% منه غير مفيد (لا أنصح به)

| البند المقترح | السبب |
|---|---|
| تنفيذ حقيقي لـ Windows/PowerShell/UI automation | نظام محاسبي للعضويات والأرصدة؛ التحكم بجهاز المستخدم ليس من وظائفه، ويوسّع سطح الهجوم في برنامج يتعامل مع المال |
| تحكم بالمتصفح (Playwright/CDP) داخل التطبيق | `@playwright/test` موجود هنا **لاختبارات E2E فقط** (بيئة CI لینكس)؛ تشغيله كأداة وكيل يحتاج متصفحاً وبيئة ويندوز لا وجود لها في CI ولا يمكن اختبارها |
| Vision Agent / رؤية الشاشة | لا يوجد حتى الآن أي مسار يقرأ الشاشة فعلاً؛ سيصير مصدراً جديداً لادعاءات بلا دليل — وهو ما يمنعه عقد `docs/AI_AGENT_AUDIT.md` P0-1 |
| نماذج رؤية محلية | قيد الذاكرة الذي ذكرته حقيقي، والحل الأنسب: إبقاء الاستدلال على API (Gemini) والبصر عند `tesseract.js`/`sharp` الموجودين |
| إعادة بناء Registry/Blackboard/Orchestrator | تكرار مباشر لما هو موجود، ويصبح سطح ذكاء **سابعاً** بعد أن وثّق التدقيق وجود ستة أسطح متوازية (`AI_AGENT_AUDIT.md:78`) |

**ملاحظة دقيقة:** نصوص المقترح تستخدم نفس مفردات المحاكاة الموجودة في الكود
(`Playwright CDP`، تنزيل ملف ثم التحقق منه) — أي أنه يبدو مستخرَجاً من العرض التجريبي،
لا من قياس تنفيذ فعلي. لذلك لا يصح اعتباره «تصميماً واقعياً» قبل التحقق.

## 3) الـ25% المفيدة: أربعة عقود تُغلق فجوة «الادعاء بلا دليل»

| # | العقد | الفجوة الحالية بالقياس | القيمة |
|---|---|---|---|
| 1 | **TaskState مشترك على الخادم** | `execute-step` يستقبل `previousResults` من العميل؛ لا حالة مُهمة على الخادم تُبنى عليها الخطوة التالية | يمنع إعادة العمل من الصفر، ويجعل «ما نعرفه» قابلاً للتدقيق |
| 2 | **عقد لكل خطوة** (`expected_state` / `timeout` / `max_retries` / `verification` / `fallback`) | الخطوات الآن `{title, tool, toolArgs}` بلا شرط نجاح معلن | يحوّل «نجح/فشل» من رأي نموذج إلى شرط قابل للفحص |
| 3 | **كاشف فشل + مُعيد تخطيط محدود** | `selfCorrectionTriggered` قيمة ينتجها النموذج، لا تحليل فشل حقيقي | يمنع الدوران اللانهائي ويوثّق سبب إعادة التخطيط |
| 4 | **بوابة دليل قبل أي «SUCCESS»** | `verificationPassed` تُصفَّر في المحاكاة (جيد)، لكن لا آلية لدليل حقيقي عند التنفيذ | تُبنى على الموجود فعلاً: `audit-chain` + `ledger-chain` + `AIProvenance` |

هذه الأربعة قابلة للتنفيذ والاختبار في CI (بلا ويندوز ولا متصفح)، وتخدم المنتج مباشرة:
`OCR → استخراج → تحقق ← دليل` و`مسودة قيد → اقتراح → تحقق توازن ← ترحيل` هما نفس النمط.

| الخيار | النطاق | التكلفة | القيمة |
|---|---|---|---|

## 5.5 حالة القرار (مُحدَّث)

✅ **نُفِّذ الخيار (ب)** بالكامل: سرب أدوات ERP الحقيقية عبر بوابة الصلاحيات، مع العقود الأربعة:
حالة المهمة على الخادم، عقد الخطوة، كاشف الفشل + إعادة تخطيط محدودة، وبوابة الدليل قبل النجاح.
التفاصيل الكاملة والدليل الحي: `docs/SWARM_ERP_TOOLS.md`.

**رُفض نهائياً** كل ما يخص التحكم بالحاسوب: PowerShell / سطر أوامر Windows، تحكم بالمتصفح (CDP)،
رؤية الشاشة، تشغيل نماذج رؤية محلية — لا صلة لها بنظام محاسبي وعلى خادم يحمل بيانات مالية.

✅ **ونُفِّذ الخيار (أ) أيضاً** بقرار المالك: تصلّب سطح AetherSwarm القائم — أربعة وكلاء حقيقيون
بأدوات من السجل، وخطة من محرّك الأدوات، وتحكيم بقاعدة أدلة، وحكم نهائي صريح، مع حذف العرض
الافتراضي الملفَّق (RTX 5090) ومحرّك المحاكاة النصية ومحاكي موارد الوكلاء.
التفاصيل والدليل: `docs/AETHER_SWARM_HARDENING.md`، والاختبارات: `test/aether-swarm.test.ts`.

**ما يزال بانتظار قرار المالك:** تدوير مفتاح Firebase المنشور في تاريخ Git (خارج نطاق المستودع)،
ومصير سطح المكتب الافتراضي داخل AetherSwarm (`WindowsDesktopWorkspace`).

## 6) قرارات تنتظر صاحب المشروع (ليست تقنية بحتة)

1. **مصير Firebase** — **حُسم (2026-09-28)**: يُبقى Firebase اختيارياً **بلا مفتاح في Git**،
   وتُقرأ تهيئته من متغيرات بيئة `VITE_FIREBASE_*`؛ وغيابها يعطّل المزامنة السحابية صراحةً
   بدل ادعاء الاتصال. الهوية الوحيدة للنظام هي JWT/PostgreSQL + سجل التدقيق المتسلسل،
   وحُذف مسار `firebase-admin` الميت من الخادم تماماً.
   **مطلوب من المالك:** تدوير المفتاح القديم المنشور في تاريخ Git (إجراء خارج المستودع).
2. **مصير السطح نفسه** — **حُسم جزئياً**: الاستثمار في AetherSwarm (الخياران أ + ب) تم،
   والقدرات غير المحاسبية (ويندوز/متصفح/رؤية شاشة) أُلغيت من الخادم ومن الوكلاء.
   **المتبقي:** سطح المكتب الافتراضي في الواجهة (`WindowsDesktopWorkspace`) — إما تحويله إلى
   عارض لنتائج أدوات ERP، أو حذفه والإبقاء على تبويب السرب والمحادثة.

## 7) كيف يُقاس النجاح إن اخترنا (أ) أو (ب)

- لكل خطوة: `expected_state` معلن، ونتيجتها تحمل `evidence[]` أو `SIMULATED` — لا `SUCCESS` عارية.
- `TaskState` تُقرأ من الخادم بعد كل خطوة (`GET /api/swarm/task/:id`) ويُبنى القرار التالي عليها.
- إعادة التخطيط محدودة (`max_retries`) ومُسجَّلة في `erpStore.auditLogs` بسبب حقيقي.
- اختبارات: سيناريو محاكاة فاشل ⇒ إعادة تخطيط واحدة ⇒ حالة نهائية `FAILED_VERIFIED` بلا ادّعاء نجاح.
