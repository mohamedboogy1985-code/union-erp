# لوحة وكيل البرمجة Jules — Union ERP

## ما الذي أُضيف؟

لوحة عربية RTL باسم **Jules — وكيل البرمجة** في القائمة الجانبية، متاحة للمدير الفعلي النشط. الاتصال الحقيقي يستخدم واجهة Jules REST الرسمية `v1alpha` عبر خادم Express، وليس Gemini SDK أو محاكاة محلية.

```text
React dashboard → /api/jules/* (JWT + admin authorization)
                → https://jules.googleapis.com/v1alpha (server-only API key)
                → repository already connected to the owner's Jules account
```

- اكتشاف المستودع المرتبط ومطابقته بمستودع واحد مسموح على الخادم.
- إنشاء مهمة بعنوان ووصف ومعايير قبول، بعد تأكيد الخصوصية.
- عرض مهام المستودع **والفرع المحددين فقط** مع الصفحات والبحث في المهام المحمّلة.
- تحميل الخطط والأنشطة، اعتماد الخطة الحالية صراحة، وإرسال الملاحظات أثناء العمل.
- عرض فروق الكود ومخرجات الأوامر والاختبارات كنص للقراءة، ورابط Pull Request إذا أعادته الخدمة.
- تحديث الجلسة المختارة كل 15 ثانية أثناء ظهور الصفحة، يتوقف بعد الانتهاء أو الخطأ.
- تسجيل أحداث الإنشاء والاعتماد وإرسال الرسائل ومحاولات الوصول المرفوضة في سجل التدقيق الحالي.

**التكامل معطّل افتراضياً.** ظهور لوحة الإعداد لا يعني أن حساب Jules متصل. `ready` في نقطة الحالة يقيس الجاهزية المحلية؛ اكتشاف المصدر هو الذي يتحقق من الوصول الفعلي. لا توجد مهام وهمية في التطبيق؛ المحاكاة موجودة في الاختبارات فقط.

## حدود مهمة قبل التفعيل

1. Jules خدمة سحابية خارجية تستنسخ المستودع المرتبط. هذا المشروع يحتوي ملفات مالية وبيانات عاملين؛ يجب مراجعة الملفات المتتبعة **وتاريخ Git** وسياسة مشاركة البيانات قبل منحه الوصول. استبعاد ملف من `.gitignore` لا يحذف نسخه السابقة. استخدم مستودعاً منقّحاً مصرحاً به إذا لزم، ولا تُعد كتابة تاريخ المستودع دون موافقة مالكه.
2. اللوحة لا ترفع قاعدة بيانات ERP أو تقاريره تلقائياً، لكن الملفات الموجودة أصلاً في Git أو البيانات التي تكتبها في وصف المهمة ستكون ضمن ما قد تصل إليه الخدمة. لا تضع بيانات شخصية أو مفاتيح أو كلمات مرور في المهام.
3. تفعيل `DEMO_MODE=false` مطلوب للاتصال الفعلي، حتى في تطبيق Electron. لا تكفي ترويسة `x-user-id` أو اختيار اسم المدير من قائمة المستخدمين.
4. هذه الإضافة لا تجعل التطبيق يعدّل نفسه: لا تنفيذ أوامر محلية، لا تطبيق patches، لا تعديل لقاعدة الإنتاج، ولا نشر أو دمج آلي.
5. لا تضع مفتاح Jules أو أسرار خادم المدير ضمن حزمة Electron موزعة؛ استخدم خدمة خلفية تديرها وتصل إليها الواجهة بالمصادقة المناسبة.
6. يُرسل `requirePlanApproval: true` دائماً، و`automationMode: AUTOMATION_MODE_UNSPECIFIED`. لا ننشئ PR آلياً؛ يُعرض رابطه إذا أصبح متاحاً من Jules. إصدار PR ومراجعته ودمجه مسؤولية مالك المستودع خارج هذه اللوحة.
7. ربط GitHub وإصدار مفتاح Jules يتطلبان إجراءات مالك الحساب. لا يمكن إنشاء ربط المستودع عبر Sources API. حدود الحصة وتوافر الخدمة وفق حساب Jules، والواجهة `v1alpha` قابلة للتغيير.

## 1. إعداد كلمة مرور المدير (دون كلمة مرور افتراضية)

أُضيف تمهيد اختياري لكلمة مرور **مستخدم مدير موجود** لأن بيانات العرض الأصلية لا تحتوي كلمات مرور. لا يُنشئ التمهيد مستخدماً جديداً ولا يمنح مستخدماً عادياً صلاحيات إضافية.

على جهازك، بعد تثبيت الاعتماديات:

```bash
npm ci --legacy-peer-deps
npm run auth:hash-password
```

يطلب الأمر كلمة المرور وتأكيدها في طرفية تفاعلية دون إظهارها. استخدم 12 حرفاً على الأقل وبحد أقصى 72 بايت UTF-8 (حد bcrypt). يطبع الأمر بصمة bcrypt فقط؛ احفظها سراً في `.env` أو مدير أسرار الخادم. لا ترسل كلمة المرور أو البصمة في المحادثات ولا تضفها إلى Git.

```dotenv
ERP_ADMIN_USER_ID=usr-mohamed-abdallah
ERP_ADMIN_PASSWORD_HASH='<bcrypt-hash-generated-locally>'
```

- معرّف المدير الافتراضي: `usr-mohamed-abdallah`، واسم دخوله الحالي: `mohamed.abdallah`.
- الحساب يجب أن يكون نشطاً، غير تجريبي، ويملك صلاحية `system:admin` حسب RBAC على الخادم.
- تقبل البصمة تكلفة bcrypt من 10 إلى 16؛ أداة التوليد تستخدم 12.
- ضع البصمة بين علامتي اقتباس مفردتين في `.env` لتجنب تفسير `$` في أدوات النشر.
- لا تظهر `passwordHash` في استجابات تسجيل الدخول أو `/api/auth/me` أو قائمة المستخدمين أو تبديلهم.
- لتغيير كلمة المرور، استبدل البصمة على الخادم وأعد تشغيله. لإبطال JWT قديمة أيضاً، دوّر `JWT_SECRET` (يُبطل جميع جلسات التطبيق).

`--legacy-peer-deps` يلائم ملف القفل الحالي للمستودع. لا تحتاج الإضافة حزم تشغيل جديدة؛ تعتمد على `fetch` الموجود في Node والمكتبات الحالية.

## 2. أسرار التشغيل الآمن

انسخ `.env.example` إلى إعدادات الخادم، دون إيداع الملف الفعلي في Git. أنشئ سرين عشوائيين مستقلين، مثلاً بتشغيل الأمر التالي مرتين محلياً:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

ثم اضبط:

```dotenv
DEMO_MODE=false
JWT_SECRET=<first-random-secret>
ENCRYPTION_KEY=<second-random-secret>
ERP_ADMIN_USER_ID=usr-mohamed-abdallah
ERP_ADMIN_PASSWORD_HASH='<bcrypt-hash>'
```

الجلسة الموثّقة تحفظ في ذاكرة الواجهة فقط، لا في `localStorage` أو روابط URL أو قائمة المزامنة دون اتصال. مسح الصفحة يتطلب تسجيل دخول جديد. تغيير مستخدم العرض يمسح التوكن الحالي. توكنات وضع العرض أو التوكنات القديمة التي لا تحمل إثبات نمط دخول كلمة المرور لا تفتح Jules حتى بعد تفعيل الوضع الصارم؛ سجّل الدخول مجدداً. بعد الدخول الموثّق يستخدم عميل API المشترك JWT أيضاً مع باقي نقاط ERP التي تدعمه.

إذا كان TOTP مفعّلاً على الحساب، تُطلب كلمة المرور **ورمز التحقق**. طلب `/api/auth/login/2fa` يتطلب الآن `password` أيضاً للحسابات ذات البصمة أو في الوضع الصارم، لمنع استخدام العامل الثاني بدلاً من كلمة المرور.

> حماية Jules لا تعني إجراء مراجعة أمنية شاملة لكل وحدات ERP القديمة. راجع بقية نقاط التطبيق وأمان الحسابات والنشر مستقلاً قبل إتاحته للعامة. حماية حالة TOTP وتخزينها تتبع آلية التطبيق الحالية.

## 3. ربط Jules والمستودع

1. بعد مراجعة الخصوصية، افتح `https://jules.google.com` وسجّل الدخول بحسابك.
2. اربط GitHub، وامنح الخدمة المستودع المطلوب فقط، لا كل مستودعات حسابك.
3. أنشئ مفتاح Jules API من إعدادات Jules. **مفتاح Gemini لا يعمل بدلاً منه.**
4. خزّن المفتاح على الخادم فقط. لا يوجد حقل لإدخاله من المتصفح ولا بادئة `VITE_` لأي سر Jules.
5. اضبط المستودع وفرع المراجعة. مثال هذه الجلسة:

```dotenv
JULES_ENABLED=true
JULES_API_KEY=<your-jules-api-key>
JULES_REPOSITORY=mohamedboogy1985-code/union-erp
JULES_STARTING_BRANCH=arena/01a07898-union-erp
```

الفرع يجب أن يكون موجوداً على GitHub ومتاحاً في Jules؛ وجوده محلياً وحده لا يكفي. هذه الإضافة لا تدفع الفروع إلى GitHub ولا تمنح الصلاحيات نيابة عنك. بعد مراجعة الملفات الحساسة، انشر عملك بالطريقة المعتمدة لديك على فرع الجلسة نفسه.

تُقرأ هوية المصدر الفعلية من Sources API، ولا تُخمّن من اسم المستودع. اسم المصدر والفرع القادم من المتصفح يُتحقق منهما على الخادم. تُحدّث معلومات الفرع من الخدمة قبل كل إنشاء.

## 4. التشغيل والاستخدام

```bash
npm run dev
# أو بعد البناء:
npm run build
npm start
```

- افتح **Jules — وكيل البرمجة** من القائمة الجانبية بأي بوابة.
- سجّل دخول المدير بكلمة مرور ERP، وليس بكلمة مرور Google.
- اضغط «تحديث» للتحقق من الإعدادات والمستودع.
- اكتب مهمة محددة، مثلاً: «أضف اختبارات لحالات القيد غير المتوازن دون تغيير القواعد المحاسبية، ثم شغّل الاختبارات الحالية».
- أكّد الخصوصية وأرسل. الإرسال ينشئ جلسة غير متزامنة؛ مهلة HTTP ليست مهلة تنفيذ المهمة.
- اختر الجلسة، اقرأ الخطة كاملة، ثم ضع علامة مراجعتها واضغط «اعتماد الخطة وبدء التنفيذ».
- يمكن إرسال ملاحظات لطلب تعديل الخطة أو الإجابة عن أسئلة Jules. الاعتماد يراجع معرّف أحدث خطة على الخادم ويرفض الخطة القديمة.
- راجع الأنشطة والاختبارات وفروق الكود، وافتح الجلسة أو رابط PR للمراجعة الخارجية. لا توجد أزرار دمج أو نشر أو تنفيذ shell هنا.

التحديث اليدوي لقائمة المهام يعيد الصفحة الأولى. «تحميل صفحة أخرى» يعمل حتى إذا كانت الصفحة الحالية فارغة بعد تصفية المستودعات الأخرى. البحث يشمل المهام المحمّلة فقط. الأنشطة تُحمّل بالكامل قبل السماح بالاعتماد، حتى 20 صفحة × 100 نشاط؛ إن تجاوزت ذلك، تُراجع من Jules مباشرة.

## API المحلية

كل المسارات الفعلية تتطلب `Authorization: Bearer <ERP JWT>` لمدير فعلي نشط ذي كلمة مرور، وتشغيل الوضع الصارم. الاستثناء الوحيد: `/status` يسمح لمدير **وضع العرض** برؤية إعدادات غير سرية، ولا يجري أي اتصال إلى Google.

| الطريقة | المسار | الوظيفة |
|---|---|---|
| GET | `/api/jules/status` | جاهزية محلية، الإعدادات غير السرية وأسباب التعطيل |
| GET | `/api/jules/sources?pageToken=...` | المستودع المسموح فقط؛ مصادر مرتبطة مسبقاً |
| GET | `/api/jules/sessions?pageToken=...` | صفحة جلسات مصفّاة بالمصدر والفرع |
| GET | `/api/jules/sessions/:id` | تفاصيل جلسة ضمن النطاق المسموح |
| GET | `/api/jules/sessions/:id/activities?pageToken=...` | الأنشطة والخطط ونتائج التنفيذ |
| POST | `/api/jules/sessions` | إنشاء مهمة بعد إقرار الخصوصية |
| POST | `/api/jules/sessions/:id/approve-plan` | اعتماد أحدث خطة بعد مراجعتها |
| POST | `/api/jules/sessions/:id/messages` | إرسال ملاحظة لجلسة لم تنتهِ |

مثال إنشاء (بيانات وصفية فقط، لا مفاتيح):

```json
{
  "title": "Add accounting edge-case tests",
  "prompt": "Add tests without changing accounting rules; run the existing suite.",
  "source": "sources/the-name-returned-by-jules",
  "startingBranch": "arena/01a07898-union-erp",
  "privacyAcknowledged": true,
  "requestId": "5d08333f-dca0-4c5d-8b24-4e2a05caad89"
}
```

اعتماد الخطة: `{ "planId": "current-plan-id", "confirmed": true, "requestId": "<new-uuid>" }`.

إرسال ملاحظة: `{ "prompt": "Add an edge case", "requestId": "<new-uuid>" }`.

- جسم طلب Jules لا يتجاوز 64 KiB. العنوان: 120 حرفاً؛ المهمة: 12000؛ الرسالة: 8000. الحقول غير المعروفة وتجاوز السياسات يُرفضان.
- `requestId` معرّف عشوائي للعملية، وليس سراً. أعد استخدامه عند تكرار **الطلب نفسه**، لا عند تغيير محتواه.
- لا يستطيع العميل تعطيل اعتماد الخطة أو تفعيل إنشاء PR آلياً بإضافة حقول إلى الطلب.
- هويات الموارد مشددة، وعنوان Google ثابت، والتحويلات HTTP ممنوعة لتجنب SSRF أو تسريب المفتاح.
- كل استجابات الوحدة تحمل `Cache-Control: no-store`. رسائل Google الخام لا تُمرر إلى العميل ولا تُسجّل، وروابط النتائج محصورة بـ Jules وPR للمستودع المسموح على GitHub.
- المخرجات تُعرض كنص لا HTML؛ لا تحميل وسائط بعيدة ولا تنفيذ للأوامر الموجودة في النتائج.

## الفشل، الحصص ومنع التكرار

| الحالة | المعنى والتصرف |
|---|---|
| `401 AUTH_REQUIRED` | الدخول غائب/منتهٍ؛ سجّل الدخول مجدداً |
| `403 JULES_FORBIDDEN` | ليس مديراً فعلياً نشطاً |
| `403 JULES_ACCOUNT_NOT_READY` | الحساب بلا بصمة كلمة مرور مناسبة |
| `503 JULES_NOT_CONFIGURED` | مفتاح/مستودع/فرع/أسرار ناقصة، أو وضع العرض مفعّل |
| `409 JULES_SOURCE_NOT_CONNECTED` | اربط المستودع المسموح من حساب Jules |
| `409 JULES_BRANCH_NOT_FOUND` | الفرع غير ظاهر في الخدمة؛ راجع GitHub/Jules |
| `409 JULES_PLAN_CHANGED` | حدّث الأنشطة وراجع الخطة الجديدة |
| `404 JULES_NOT_FOUND` | مورد محذوف أو خارج المستودع/الفرع المسموحين |
| `429` | حد محلي أو حصة Jules؛ احترم `Retry-After` |
| `502 JULES_ACCESS_DENIED` | راجع مفتاح Jules وصلاحياته (ليست مشكلة JWT المحلي) |
| `502/504` مع `outcomeUnknown: true` | قد تكون عملية الكتابة قُبلت؛ راجع Jules قبل أي إعادة إرسال |

- المهلة: 20 ثانية **لكل استدعاء HTTP**، وحد الاستجابة 4 MiB.
- حد محلي لكل مدير: 90 قراءة و20 كتابة في الدقيقة، دون استثناء للمدير؛ لا يتجاوز حدود حساب Jules.
- لا توجد إعادة محاولة تلقائية لعمليات الكتابة، ولا جدولة أو webhooks ضمن هذا الإصدار.
- نافذة منع تكرار العمليات: 10 دقائق، حتى 200 عملية، في ذاكرة **عملية خادم واحدة**. تُحفظ النجاحات والأخطاء ذات النتيجة غير المؤكدة؛ الأخطاء المؤكدة التي لم تقبل العملية تسمح بمحاولة لاحقة وفق الحصة.
- هذه النافذة ليست ضماناً لـ exactly-once بعد إعادة تشغيل الخادم أو بين عدة نسخ أو بعد انتهاء المدة. للنشر متعدد النسخ أضف مخزناً مشتركاً مع قفل موزع قبل تفعيل إرسال آلي كثيف.
- لا تُنشئ معرّفاً جديداً لمهمة غامضة النتيجة لتجاوز الحماية. راجع قائمة الجلسات في Jules أولاً. الواجهة تحتفظ بالمسودة عند الفشل ولا تعيد إرسالها تلقائياً.
- أحداث التدقيق تستخدم هوية JWT، لا `x-user-id`. لا يُحفظ وصف المهمة أو الرسالة أو محتوى الخطة أو المفتاح في سجل التدقيق. تُضاف الأحداث إلى `erpStore.auditLogs`، ويُستدعى مخزّن PostgreSQL الحالي عند تهيئته. الحفظ في القاعدة أفضل جهد وفق آلية ERP، وتعذّره لا يعيد إرسال مهمة إلى Google. في وضع الذاكرة فقط لا يبقى السجل بعد إعادة التشغيل؛ تحميل السجلات التاريخية وعرضها يتبع آلية ERP الحالية.

## التعطيل والطوارئ

اضبط `JULES_ENABLED=false` وأعد تشغيل الخادم. دوّر/ألغِ المفتاح من إعدادات Jules إذا اشتبهت بتسريبه. تعطيل اللوحة **لا يلغي جلسات جارية لدى Google**؛ راجعها من Jules. حذف الجلسات وإيقافها آلياً غير مُنفّذ لتجنب الخلط بين حذف سجل وإلغاء تنفيذ فعلي.

## التحقق والاختبارات

```bash
npm run test:jules
npm test
npm run typecheck:jules
npm run build
```

اختبارات الوحدة وHTTP وواجهة React تستخدم استجابات محاكاة ولا تحتاج مفتاحاً ولا تتصل بـ Google. تغطي المصادقة وTOTP والصلاحيات ووضع العرض وتقييد المستودع/الفرع واعتماد الخطط ومنع التكرار والصفحات والحصص والمهل وتسريب المفاتيح وحقن HTML والردود القديمة بعد تبديل المهام.

الاختبار الحي من البداية إلى النهاية يتطلب إعداد حسابك والمستودع والمفتاح، ثم إنشاء مهمة صغيرة على الفرع المسموح بعد مراجعة الخصوصية. نجاح الاختبارات المحاكاة ليس دليلاً على تفعيل حساب Google.

فحص `typecheck:jules` محدود بملفات التكامل وتبعياتها. الفحص العام للمستودع قد يعرض أخطاء سابقة غير مرتبطة بهذه الوحدة، ويجب التعامل معها بصورة مستقلة.

## الملفات الأساسية

- `server/services/jules.service.ts`: عميل REST، سياسات المصدر/الفرع، تطبيع الردود والمهل ومنع التكرار.
- `server/routes/jules.routes.ts`: JWT وRBAC وحدود الطلبات والتدقيق وواجهات ERP.
- `src/pages/JulesDashboard.tsx`: اللوحة العربية والتسجيل ومراجعة الخطط والأنشطة.
- `src/services/jules-api.ts`: عميل same-origin والتحميل الآمن للصفحات.
- `server/security/admin-credentials.ts` و`scripts/hash-password.mjs`: إعداد مدير حقيقي دون كلمة مرور افتراضية.
- `test/jules.test.ts` و`test/jules-ui.test.tsx`: اختبارات دون شبكة خارجية.

### معاينة التطوير المضمّنة

للمعاينة داخل بيئة تطوير سحابية فقط يمكن تشغيل `ALLOW_PREVIEW_EMBED=true` مع `NODE_ENV=development` للسماح بإطار المعاينة. لا يغيّر هذا السلوك حماية الإطارات في الإنتاج، ولا يتجاوز قفل Jules في وضع العرض. يربط الخادم المنفذ بـ `0.0.0.0` ويسمح Vite بمضيفات `.e2b.app`؛ جميع طلبات المتصفح تبقى نسبية.
